# Уведомления о находках диагностики

`tnt-notifier` носит находки диагностики кластера дежурному. Находка
появилась — тревога, ушла — отбой, держится долго — напоминание не чаще
заданного срока. Куда носить, решают приёмники: журнал узла, файл,
служба по HTTP, письмо — или свой.

```lua
local notifier = require('tnt.notifier')
notifier.configure({ sinks = { notifier.log.new(), notifier.http.new({ url = 'https://alerts.example.org/hook' }) } })
require('tnt.cluster').configure({ on_issues = notifier.on_issues })
```

Находки приносит диагностика
[`tnt-cluster-health`](https://github.com/tnt-skein/tnt-cluster-health):
её обход зовёт `on_issues` после каждого удачного прохода, и уведомитель
встаёт в этот хук без обёрток. Годится и любой другой источник, который
отдаёт находки тем же списком.

Зависит от [`tnt-clock`](https://github.com/tnt-skein/tnt-clock)
(стенные и монотонные часы),
[`tnt-disk`](https://github.com/tnt-skein/tnt-disk) (дозапись файла),
[`tnt-http`](https://github.com/tnt-skein/tnt-http) (клиент HTTP),
[`tnt-log`](https://github.com/tnt-skein/tnt-log) (журнал),
[`tnt-mail`](https://github.com/tnt-skein/tnt-mail) (письмо),
[`tnt-must`](https://github.com/tnt-skein/tnt-must) (проверка настроек)
и [`tnt-external`](https://github.com/tnt-skein/tnt-external)
(подмена часов, реестра, диска и клиента в проверках).

## Зачем пакет

Диагностика знает о кластере всё, что нужно, и рассказывает об этом
тому, кто спросит. Беда в том, что ночью не спрашивает никто: находка
живёт в панели, а человек спит — и узнаёт о ней утром, вместе
с последствиями. Уведомитель переворачивает это: не человек ходит
за находками, а находки идут к человеку.

Пакет делает для этого пять вещей:

- **Рассказывает о перемене, а не о каждом обходе.** Обход идёт раз
  в несколько секунд, и одна незакрытая находка за ночь превратилась бы
  в тысячи писем. Уведомление уходит, когда находка появилась и когда
  ушла.
- **Шлёт отбой.** Уход находки — событие не менее важное, чем
  появление: человек, получивший ночью тревогу и не получивший отбоя,
  поедет в офис.
- **Напоминает о долгоживущей находке.** Не чаще заданного срока —
  ровно чтобы она не выглядела забытой. Срок меряется монотонными
  часами: перевод стенных не глушит напоминания и не выпускает их разом.
- **Отказ приёмника не роняет обход и не мешает остальным.** Приёмники
  не связаны между собой ничем, кроме общего списка находок, и общая
  остановка из-за одного означала бы, что худший решает за всех.
- **Проводит находки через встроенный реестр проверок готовности.**
  Отказ проверки Tarantool поднимает предупреждением конфигурации, и там,
  где настроен Prometheus, тревога работает без единого приёмника.

## Как пользоваться

Примеры ниже независимы: каждый начинается с пустой памятью уведомителя,
а `catcher`, `told` и `finding` в них — из примера «Тревога, отбой,
напоминание».

### Находки обхода: `on_issues`

`notifier.on_issues(issues)` разбирает находки одного обхода. Первый
аргумент — список находок; остальные, которые передаёт хук диагностики
(сводка и снимок), уведомитель не читает. Вместо списка можно передать
`nil` — это обход без находок.

Находка — таблица:

| Поле | Что |
|---|---|
| `id` | опознаватель находки: по нему уведомитель узнаёт её на следующих обходах; без него находка пропускается |
| `severity` | серьёзность: `warning` или `critical` |
| `rule` | правило, которое её нашло |
| `scope` | о чём она: `instance`, `replicaset`, `cluster` |
| `instance`, `replicaset` | о каком узле и репликасете, если о каком-то |
| `message` | что случилось, словами |

Звать `on_issues` можно и самому — с находками, собранными как угодно:

```lua
local notifier = require('tnt.notifier')

notifier.configure({ sinks = { notifier.log.new() } })

notifier.on_issues({
    {
        id = 'replication:instance:storage-001-a',
        rule = 'replication',
        scope = 'instance',
        instance = 'storage-001-a',
        replicaset = 'storage-001',
        severity = 'critical',
        message = 'реплика отстала',
    },
})
--> в журнале узла, уровнем warn:
--> находка raised id=replication:instance:storage-001-a instance=storage-001-a message="реплика отстала" severity=critical
```

Находка без опознавателя пропускается: её не отличить от такой же
соседней, и напоминания с отбоями по ней уходили бы наугад.

### Тревога, отбой, напоминание

Событие уходит на перемену состояния находки:

| Состояние | Константа | Когда |
|---|---|---|
| `raised` | `notifier.RAISED` | опознавателя ещё нет в памяти: находка появилась |
| `reminded` | `notifier.REMINDED` | находка всё ещё здесь, и с прошлого рассказа о ней прошло `repeat_after` секунд |
| `resolved` | `notifier.RESOLVED` | находки нет в обходе: она ушла и забывается |

На остальных обходах уведомитель молчит, но помнит последний вид
находки: отбой и напоминание несут её последнее сообщение, а не первое.
Вернувшаяся находка — снова тревога: ушла и вернулась — это новая беда,
а не продолжение старой.

```lua
local told = {}
local catcher = {
    name = 'ловец',
    send = function(event)
        table.insert(told, event.state)
    end,
}
local finding = { id = 'disk:instance:storage-001-b', severity = 'critical', message = 'каталог данных исчез' }

notifier.configure({ sinks = { catcher }, repeat_after = 1 })

notifier.on_issues({ finding }) -- raised
notifier.on_issues({ finding }) -- тишина: находка уже рассказана
require('fiber').sleep(1.5)
notifier.on_issues({ finding }) -- reminded: срок в секунду прошёл
notifier.on_issues({}) -- resolved
notifier.on_issues({ finding }) -- raised: вернулась

--> told = { 'raised', 'reminded', 'resolved', 'raised' }
```

Срок — «через столько и позже», а не «ровно через столько»: обход мог
не дойти до находки несколько часов, и напоминание уйдёт на первом
обходе после срока.

### Настройка: `configure`

```lua
notifier.configure({
    sinks = { notifier.log.new(), notifier.file.new({ path = '/var/log/tarantool/alerts.jsonl' }) },
    min_severity = 'critical',
    repeat_after = 1800,
    capacity = 4096,
    resolve = true,
})
```

| Поле | Что | Какое | По умолчанию |
|---|---|---|---|
| `sinks` | приёмники, в порядке отправки | список приёмников | `{}` — никуда |
| `min_severity` | с какой серьёзности слать: `warning` или `critical` | строка | `'warning'` |
| `repeat_after` | через сколько секунд напоминать о находке, которая никуда не делась | число больше нуля | `3600` |
| `capacity` | сколько находок помнить | целое больше нуля | `1024` |
| `resolve` | слать ли отбой; `false` — не слать | `true` или `false` | `true` |

Каждый вызов задаёт настройку заново: не названное в нём возвращается
к умолчанию. Память о рассказанном вызов не трогает — уже известные
находки не рассказываются заново. Модуль настраивает себя умолчаниями
при загрузке: без `configure` находки помнятся, но уходить им некуда.

Негодная настройка — бросок на строке того, кто звал `configure`,
а прежние настройки при этом остаются: всё проверяется раньше, чем
меняется. Настройки пишет программист, и ошибка в них — его ошибка;
а дошедшая до обхода, она осталась бы записью в журнале: хук диагностики
зовёт уведомитель под `pcall`, и уведомления просто перестали бы уходить.
Бросают:

- не таблица вместо настроек и незнакомый ключ — опечатка в имени
  настройки иначе молча оставила бы умолчание;
- значение не того типа из таблицы выше;
- `repeat_after`, равный нулю или меньше: при нуле напоминание уходило бы
  на каждом обходе, то есть шумом, от которого уведомитель и спасает;
- `capacity`, равный нулю или меньше: такой потолок забывал бы всё
  на каждом обходе, и каждая живая находка была бы новой тревогой;
- приёмник без списка — `sinks = notifier.log.new()` вместо
  `sinks = { notifier.log.new() }`: таблицу приёмника обходили бы как
  пустой список, и уведомления не уходили бы никуда;
- приёмник без имени-строки или без отправки (о них — в «Приёмниках»).

```lua
-- init.lua
local notifier = require('tnt.notifier')

notifier.configure({ repeat_after = '1800' })
--> init.lua:4: настройки уведомителя.repeat_after — число больше 0, а не строка

notifier.configure({ sinks = notifier.log.new() })
--> init.lua:7: настройки уведомителя.sinks — массив, а не таблица с ключом «name»

notifier.configure({ repeat_afer = 60 })
--> init.lua:10: настройки уведомителя: ключа «repeat_afer» нет, есть capacity, min_severity, repeat_after, resolve, sinks
```

Место — строка вызывающего, а не строка внутри пакета: ошибка в вызове,
и искать её надо там. Позванный прямо из `pcall(notifier.configure, …)`
вызов места не ставит вовсе: вызывающий там — сам `pcall`.

Слово в `min_severity` со словарём не сверяется — только то, что это
строка: порог не из словаря не отсекает никого (ниже, «Порог
серьёзности»). `box.NULL` — так приходит пустое значение из YAML и JSON —
значит «не задано», как и отсутствие ключа. Список приёмников берётся
копией: приёмник, дописанный в него после настройки, в отправку
не попадёт.

Час напоминания — середина между двумя бедами: реже — и находка
выглядит забытой, чаще — и напоминания сами становятся шумом, от
которого отписываются.

### Порог серьёзности

Уровни идут от тихого к громкому: `warning`, `critical`. Порог — «от и
громче»: при `min_severity = 'critical'` проходит только тревога. Слова
сравниваются порядком в списке, а не по алфавиту: `critical` по алфавиту
меньше `warning`, и сравнение слов однажды пропустило бы предупреждение,
отбросив тревогу.

```lua
told = {}
notifier.configure({ sinks = { catcher }, min_severity = 'critical' })

notifier.on_issues({
    { id = 'memory:instance:storage-001-a', severity = 'warning', message = 'память занята на 87 %' },
    { id = 'unreachable:instance:storage-001-c', severity = 'critical', message = 'узел не отвечает' },
})

--> told = { 'raised' } — только о недоступном узле
```

Слова вне словаря разбираются в разные стороны:

- **серьёзность находки** не из словаря не будит никого: правило, чей
  уровень не разобран, — это правило, о котором не известно ничего,
  включая то, насколько оно срочное. Такая находка не запоминается;
- **порог** не из словаря не отсекает никого: молчать обо всём из-за
  опечатки в настройке хуже, чем шуметь.

Находка, чья серьёзность упала ниже порога, для уведомителя ушла:
уходит отбой. Поднимется снова — снова тревога.

### Событие

Приёмник получает событие — таблицу, одну на все приёмники:

| Поле | Что |
|---|---|
| `state` | `raised`, `reminded` или `resolved` |
| `at` | когда, по стенным часам: секунды от эпохи с дробью |
| `id`, `severity`, `rule`, `scope`, `instance`, `replicaset`, `message` | поля находки как есть |

Поле, которого в находке нет, в событии тоже пустое. Вид события один
на все приёмники: иначе журнал, файл и служба однажды разъехались бы
в том, что они называют находкой.

### Приёмники

Приёмник — таблица с именем и отправкой:

```lua
local sink = {
    name = 'дежурному',
    send = function(event)
        -- пусто — принято; строка — причина отказа
        return nil
    end,
}
```

Имя — строка, отправка — функция либо таблица с `__call`; без них
`configure` бросает (`настройки уведомителя.sinks[2].send — функция или
вызываемая таблица, а не nil`: номер — место приёмника в списке). Имя
едет в журнал при отказе: с двумя приёмниками иначе не понять, который
из них молчит. Отказ — строка из `send` или исключение в ней: уведомитель
пишет его в журнал и идёт к следующему приёмнику.

Приёмники пакета проверяют свои настройки при сборке, тем же порядком:
негодное значение или незнакомый ключ — бросок на строке того, кто звал
`new`. Приёмник без адреса отказывал бы на каждом событии, и видно это
было бы только в журнале. `box.NULL` в их настройках тоже значит
«не задано», а сами настройки берутся копией: правка таблицы после
сборки до приёмника не доезжает.

Четыре приёмника приходят с пакетом: `notifier.log`, `notifier.file`,
`notifier.http` и `notifier.mail`.

#### Журнал узла: `notifier.log.new()`

Приёмник, который работает всегда: сети может не быть, каталога может
не быть, а журнал у узла есть с первой секунды. Толку от него меньше,
чем от письма, — но «никуда не слать» хуже, чем «слать туда, где хотя бы
останется след».

Запись — `находка <состояние>` с полями `id`, `severity`, `instance`,
`message`, журналом `tnt.notifier`. Тревога и предупреждение пишутся
уровнем `warn`, серьёзность вне словаря — `info`. Ошибкой не пишется
ничего: ошибка в журнале узла значит, что сломался сам узел, а здесь
сломалось что-то в кластере, и узел об этом рассказывает. Имя
приёмника — `log`.

#### Файл: `notifier.file.new({ path, name })`

Строка JSON на событие, дозаписью в конец: события идут вперёд,
и переписывание потеряло бы всё, что было до него. Файл читают и человек,
и агент выгрузки, который умеет слать письма и вести дежурство, — узлу
о них знать не обязательно.

```lua
local fio = require('fio')
local json = require('json')

local path = fio.pathjoin(fio.tempdir(), 'alerts.jsonl')
local file = notifier.file.new({ path = path })

file.send({ state = 'raised', id = 'disk:instance:storage-001-b', severity = 'critical' })
file.send({ state = 'resolved', id = 'disk:instance:storage-001-b', severity = 'critical' })

local lines = {}

for line in io.lines(path) do
    table.insert(lines, json.decode(line).state)
end

--> lines = { 'raised', 'resolved' }
```

Путь не выдумывается: файл уведомлений рядом с данными узла — это файл,
который никто не читает. `path` — непустая строка, `name` — строка;
без пути приёмник не собирается:

```lua
-- init.lua
local notifier = require('tnt.notifier')

notifier.file.new({})
--> init.lua:4: настройки приёмника file.path — непустая строка, а не nil
```

Отказ записи — текстом отказа
[`tnt-disk`](https://github.com/tnt-skein/tnt-disk). Имя по умолчанию —
`file`.

#### Служба по HTTP: `notifier.http.new({ url, timeout, headers, name })`

`POST` с событием в теле JSON — тот крючок, в который вешают дежурство:
Alertmanager, чат, собственный сборщик.

| Поле | Что | Какое | По умолчанию |
|---|---|---|---|
| `url` | куда слать | непустая строка | — |
| `timeout` | сколько секунд ждать ответа | число больше нуля | `2` |
| `headers` | свои заголовки запроса; `content-type` по умолчанию `application/json`, свой — главнее | имя — строка, значение — строка или число | `{}` |
| `name` | имя приёмника | строка | `'http'` |

Заголовки берутся копией, и таблица вызывающего остаётся как была:
дописанный в неё тип тела уехал бы потом и в его собственный запрос.
Имена в копии — в нижнем регистре, поэтому свой `Content-Type` главнее
нашего при любом написании. Значение-число клиент приводит к строке сам;
прочее он отверг бы только при отправке, на каждом событии, — поэтому
оно отвергается броском здесь:

```lua
-- init.lua
local notifier = require('tnt.notifier')

notifier.http.new({ url = 'https://alerts.example.org/hook', timeout = '2' })
--> init.lua:4: настройки приёмника http.timeout — число больше 0, а не строка

notifier.http.new({ url = 'https://alerts.example.org/hook', headers = { ['x-tags'] = { 'db' } } })
--> init.lua:7: настройки приёмника http.headers.x-tags — строка или число, а не таблица
```

Срок короче миллисекунды и бесконечный проверка пропускает как числа
больше нуля, а клиент HTTP их не примет: отправка упадёт, и отказ
ляжет в журнал — `уведомление не доставлено`.

Удача — любой ответ `2xx`: службы отвечают и 200, и 202, и 204,
а различать их незачем. Отказы:

| Отказ | Когда |
|---|---|
| `служба не ответила: <причина>` | нет соединения, вышел срок |
| `служба ответила <код>` | ответ вне `2xx`, в том числе переход `3xx` |

Переход по `Location` приёмник не проходит: на 301 и 302 клиент по
правилам HTTP пошёл бы дальше методом `GET` и без тела, служба по новому
адресу ответила бы 200, и событие, которого она не получила, числилось бы
доставленным. Переход — отказ со своим кодом в журнале, и адрес службы
правится в настройке.

```lua
local server = require('http.server').new('127.0.0.1', 18095, { log_requests = false })
local taken = {}

server:route({ path = '/hook', method = 'POST' }, function(request)
    table.insert(taken, { event = request:json(), token = request.headers['authorization'] })

    return { status = 202 }
end)
server:start()

local hook = notifier.http.new({
    url = 'http://127.0.0.1:18095/hook',
    headers = { authorization = 'Bearer слово' },
})

hook.send({ state = 'raised', id = 'disk:instance:storage-001-b', message = 'каталог данных исчез' })
--> nil — служба приняла; taken[1].event.message = 'каталог данных исчез', taken[1].token = 'Bearer слово'

server:stop()

notifier.http.new({ url = 'http://127.0.0.1:1/hook', timeout = 0.5 }).send({ state = 'raised' })
--> 'служба не ответила: POST http://127.0.0.1:1/hook: сервер не ответил: Could not connect to server (код 595)'
```

Срок короткий нарочно, а повторов нет вовсе: почему — в «Чем пришлось
поступиться». Клиент собирается на каждую отправку заново, с этим сроком
и без повторов и переходов.

#### Письмо: `notifier.mail.new({ to, from, name })`

Тот случай, ради которого уведомитель и писался: ночью в панель
не смотрит никто, а письмо будит телефон. Письмо уходит почтой
[`tnt-mail`](https://github.com/tnt-skein/tnt-mail) — сервер
и отправителя по умолчанию задаёт её `configure`, а получателя — сам
приёмник: у дежурного свой адрес, и он не тот, на который узел шлёт
отчёты.

```lua
local mail = require('tnt.mail')

mail.configure({ from = 'tarantool@example.org', smtp = { host = '127.0.0.1', port = 1025 } })

local letters = notifier.mail.new({ to = 'duty@example.org' })

letters.send({
    state = 'raised',
    id = 'replication:instance:storage-001-a',
    rule = 'replication',
    severity = 'critical',
    instance = 'storage-001-a',
    replicaset = 'storage-001',
    message = 'реплика отстала',
})
--> nil — письмо ушло
```

Тема собрана так, чтобы её хватало вместо письма: по уведомлению
на экране блокировки человек понимает, что случилось и насколько срочно,
не открывая почту. Слово состояния — первым и по-русски: почтовые
программы обрезают тему справа, и главное слово обязано уцелеть.

```
[ТРЕВОГА] storage-001-a: реплика отстала
```

| Состояние | Слово в теме |
|---|---|
| `raised` | `ТРЕВОГА` |
| `reminded` | `всё ещё` |
| `resolved` | `отбой` |

Вместо узла тема называет репликасет, а без обоих — `кластер`. В теле —
всё, что известно о находке, в столбик: человек читает это с телефона
и не может спросить уточнений.

```
Находка: реплика отстала
Состояние: raised
Серьёзность: critical
Правило: replication
Узел: storage-001-a
Репликасет: storage-001
Опознаватель: replication:instance:storage-001-a
```

Строки «Узел» и «Репликасет» — только когда они в находке есть.

`to` и `from` — адреса так, как их понимает почта: строка, таблица
`{ address = …, name = … }` или список таких. Получатель обязателен —
получатели почты по умолчанию не дежурный, — а без `from` письмо уходит
от отправителя почты по умолчанию:

```lua
-- init.lua
local notifier = require('tnt.notifier')

notifier.mail.new({ from = 'tarantool@example.org' })
--> init.lua:4: настройки приёмника mail.to — строка или таблица, а не nil
```

Отказ почты — её текстом. Имя по умолчанию — `mail`.

`notifier.mail` берётся при загрузке под `pcall`: если почта в процессе
не загружается, поле пустое, а остальные приёмники и сам уведомитель
работают как прежде.

### Отказ приёмника

Упавший или отказавший приёмник становится записью в журнале, а не
исключением в обходе: `уведомление не доставлено` уровнем `warn` с именем
приёмника, состоянием события и причиной. Следующие приёмники получают
событие как ни в чём не бывало.

```lua
told = {}
notifier.configure({
    sinks = {
        {
            name = 'падучий',
            send = function()
                error('служба не отвечает', 0)
            end,
        },
        catcher,
    },
})

notifier.on_issues({ finding })
--> в журнале: уведомление не доставлено err="служба не отвечает" sink=падучий state=raised
--> told = { 'raised' } — второй приёмник событие получил
```

Отказ не повторяется: следующий обход о той же находке промолчит, пока
не придёт срок напоминания или отбой.

### Находки во встроенном реестре проверок готовности

`notifier.publish_health_checks()` делает каждую находку, которую помнит
уведомитель, проверкой готовности `cluster.findings.<опознаватель>`
во встроенном реестре Tarantool. Проверка не проходит, пока находка
жива, и называет её серьёзность и сообщение. Её отказ ядро поднимает
предупреждением конфигурации — оно видно в `config:info().alerts`
и в числе `tnt_config_alerts`. Нужен узел, поднятый по конфигурации.

```lua
notifier.configure({ sinks = { catcher } })
notifier.on_issues({ finding })
notifier.publish_health_checks()

local alerts = require('config'):info().alerts
--> alerts[1].message:
--> Readiness health check "cluster.findings.disk:instance:storage-001-b" failed: critical: каталог данных исчез

notifier.on_issues({}) -- находка ушла: проверка снята, предупреждения нет
notifier.withdraw_health_checks()
```

Проверки следуют за находками: новая заводится на обходе, где находка
появилась, ушедшая снимается, долгоживущая называет последнее сообщение —
предупреждение с вчерашним сообщением хуже, чем никакое. Уже известные
находки заводятся сразу при вызове, а не на следующем обходе. Повторный
вызов ничего не меняет.

`notifier.withdraw_health_checks()` снимает все проверки о находках
и больше их не заводит; снятие без проведения молчит.

Что учтено:

- **Перечитывание конфигурации.** В Tarantool 3.8 оно стирает доску
  предупреждений, а реестр помнит, что предупреждение поднято, и второй
  раз его не поднимает. Уведомитель подписан на `config.info` и на каждое
  событие заводит свои проверки заново — предупреждение поднимается
  с нуля.
- **Находки правила `configuration`** в реестр не идут. Такая находка
  пересказывает предупреждения конфигурации узла: о чужом узле она и так
  предупреждение там, где случилась, а о своём пересказала бы наши же
  предупреждения, из них родилась бы новая находка, и сообщение росло бы
  с каждым обходом.
- **Имя с `cluster.`** Так проверки узнаёт проба готовности
  [`tnt-health`](https://github.com/tnt-skein/tnt-health): `/health/ready`
  проверок `cluster.*` не спрашивает и не снимает с балансировки узел,
  на котором живёт уведомитель, за беды соседей.
- **Отказ реестра** пишется в журнал (`находка не заведена проверкой
  готовности`), и находка пробуется заново на следующем обходе.

Включают это на узле уведомителя, а не на всех, и не даром: встроенная
готовность такого узла из-за беды соседа — «не готов»,
`box.info.health.readiness.status` — `false`. Всякий, кто читает
`box.info.health` сам, увидит неготовый узел.

### Что с уведомлениями: `status`, `size`, `forget`

```lua
notifier.configure({ sinks = { notifier.log.new(), catcher }, min_severity = 'critical', repeat_after = 120 })
notifier.on_issues({ finding })

notifier.status()
--> {
-->     sinks = { 'log', 'ловец' },
-->     min_severity = 'critical',
-->     repeat_after = 120,
-->     resolve = true,
-->     known = 1,
--> }

notifier.size() --> 1 — сколько находок помнится
notifier.forget() -- забыть рассказанное: следующий обход расскажет обо всём заново
notifier.size() --> 0
```

`forget` снимает и проверки о находках в реестре, если находки
проводятся.

### Потолок памяти

Уведомитель помнит не больше `capacity` находок. Потолок нужен не от
злого умысла, а от кластера на сотню узлов с десятком правил: список
находок там растёт быстрее, чем кажется. Ровно `capacity` — ещё
не переполнение; больше — и уведомитель забывает всё разом с записью
`находок больше, чем помещается в память` уровнем `warn`.

```lua
local a = { id = 'a', severity = 'warning' }
local b = { id = 'b', severity = 'warning' }
local c = { id = 'c', severity = 'warning' }

notifier.configure({ sinks = { catcher }, capacity = 2 })

notifier.on_issues({ a, b })
notifier.size() --> 2

notifier.on_issues({ a, b, c })
notifier.size() --> 0 — забыто всё
```

Выбирать, кого забыть, не из чего: находки одного обхода приходят одной
секундой, и «самая старая» среди них — просто та, что попалась первой.
Переполнение значит другое: кластер в беде целиком, и о находках
расскажут заново на следующем обходе.

### Подмена в проверках

Внешние зависимости объявлены через
[`tnt-external`](https://github.com/tnt-skein/tnt-external) и подменяются
`_set_source` по имени; `_set_source(nil)` возвращает настоящие.

| Модуль | Имя | Что |
|---|---|---|
| `tnt.notifier` | `now` | стенные часы — дата события |
| | `monotonic` | монотонные часы — срок напоминания |
| | `registry` | функция, отдающая встроенный реестр проверок готовности |
| | `watch` | подписка на событие `config.info` |
| `tnt.notifier.sink.file` | `append` | дозапись строки в файл |
| `tnt.notifier.sink.http` | `client` | функция от срока, отдающая клиент HTTP с методом `post` |

```lua
local moment = 100

notifier._set_source({
    monotonic = function()
        return moment
    end,
})

-- ... проверка двигает moment вместо того, чтобы ждать час ...

notifier._set_source(nil)
```

Настоящий клиент приёмника HTTP собирает `notifier.http._default_client(timeout)`:
им проверяется, что умолчание — настоящий клиент с выключенными
повторами и переходами, а не подмена.

## Чем пришлось поступиться

- **Отправка — в файбере обхода.** Приёмники зовутся по очереди, прямо
  в `on_issues`, и медленная служба держит весь обход. Поэтому срок
  приёмника HTTP — две секунды: служба, отвечающая минуту, остановила бы
  диагностику на эту минуту — то есть сломала бы то, о чём пришла
  рассказать. Десятки новых находок при лежащей службе — всё равно
  десятки таких сроков подряд; кому это дорого, тот отдаёт событие
  из `send` в свою очередь и возвращается сразу.
- **Повторов и очереди нет.** Неотправленное пришлось бы где-то держать,
  а очередь пережила бы перезапуск не лучше самой находки. Отказ
  приёмника пишется в журнал, и событие пропадает: следующий раз о той
  же находке скажет напоминание или отбой. Клиент HTTP берётся с явно
  выключенными повторами — его умолчание разумно для чужого API, но
  не для уведомления.
- **Память живёт в процессе.** После перезапуска узла все живые
  находки — снова тревога, а отбоя по находкам, ушедшим, пока узел
  лежал, не будет. Уведомитель держат на одном узле — на том, где идёт
  обход: на каждом узле он слал бы свои копии тех же событий.
- **Окна подтверждения нет.** Тревога уходит на первом обходе с находкой,
  отбой — на первом без неё. Мигающая связь даёт пару писем на каждое
  мигание; `repeat_after` гасит только долгоживущую находку.
- **Переполнение забывает всё.** Следующий обход рассказывает обо всём
  заново — шум, но не потеря; выбирать, кого забыть, не из чего.
- **Реестр проверок — внутренний модуль ядра.** Публичного способа
  поднять своё предупреждение конфигурации у Tarantool нет, эта дверь
  единственная; уведомитель берёт её при надобности, и без реестра
  всё остальное работает. Цена — неготовность узла уведомителя в
  `box.info.health`, пока в кластере есть находки.

## Проверки

Проверки лежат в `test/` и идут на luatest: `.rocks/bin/luatest test/`.
Модули пакета берутся из исходников, зависимости — установленными.

В процессе проверок — уведомитель на подменённых часах и двойнике
реестра: тревога, тишина, отбой и его выключение, возврат находки,
напоминание на границе срока и после долгого молчания, перевод стенных
часов в обе стороны, порог на границе и вне словаря, серьёзность вне
словаря, находка без опознавателя, падающий и отказывающий приёмник,
потолок памяти на границе и по умолчанию, состояние, забвение;
проверка настроек — бросок с местом вызывающего на не таблице,
незнакомом ключе, значении не того типа, нулевом сроке и потолке,
приёмнике без списка, без имени и без отправки, прежние настройки после
броска, `box.NULL` как «не задано», список приёмников копией;
проверки в реестре — заведение сразу и по обходу, последнее сообщение,
снятие ушедшей, эхо правила `configuration`, прежняя проверка с тем же
именем, отказ реестра и повтор, снятие при переполнении и забвении,
отзыв и перезаведение на событие `config.info`; настоящий реестр ядра
без уступки файбера. Приёмники: уровни журнала, дозапись файла и его
отказы, запрос HTTP на двойнике клиента — тело, заголовки, срок, границы
`2xx` с обеих сторон, код не числом, — настоящий клиент по умолчанию
без повторов, письмо на подменённой отправке почты — тема по состоянию,
узлу, репликасету и кластеру, тело, отказы; у каждого приёмника — бросок
на негодных настройках с местом вызывающего, `box.NULL` как «не задано»,
настройки копией; заголовки HTTP — таблица вызывающего не меняется,
свой тип тела главнее при любом регистре имени.

Две группы живые. Первая поднимает узел по декларативной конфигурации:
находка становится предупреждением конфигурации, переживает
перечитывание и уходит с отбоем. Вторая шлёт событие настоящему серверу
HTTP: служба приняла, служба отказала, служба ответила переходом — и по
нему не ходили, — адрес молчит. Рок `http` для неё ставит `make deps`.

Покрытие строк — 100 %, убитых мутантов — 100 % (84 проверки; 110
мутантов в шести модулях). Примеры этого документа прогнаны на Tarantool
3.8 на узле, поднятом по конфигурации: служба HTTP — живой сервер `http`,
письмо — приёмник SMTP на том же узле, разобранный обратно `tnt-mail`.
